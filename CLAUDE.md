## The two editor PWAs are the source of truth

Rob does mural and route editing through two custom PWAs in `tools/`. They
emit paste-ready blocks that I apply verbatim. **Do not bypass them by running
build scripts** — see the gotcha section below.

### `tools/yaml-editor.html`
Edits mural YAMLs (bio, GPS, IG, etc.). Exports start with
`# ═══ Modified YAML Files ═══`. Each mural block is the full new YAML; apply
by overwriting `data/murals/{id}-{slug}.yaml`. After applying:

- Run `python3 scripts/build-data.py` to regenerate `js/data.js`.
- If a YAML was renamed, update `data/murals/_index.json` (maps id → filename).
- Validate: `python3 -c "import yaml; yaml.safe_load(open(path))"`.

### `tools/route-editor.html`
Edits tour routes — stops, paths, mural lat/lng nudges. **Routes are now data
(v1.7):** the canonical source is `data/routes.json` and routes ship **over OTA**
like mural data — no app build. Exports come in three sections:

1. `# ═══ GPS Position Updates ═══` — `lat:` / `lng:` lines per mural, and/or a
   `facing:` line (the VIEW direction: degrees you look to see the mural, 0 = N — the
   wall faces the opposite way; set with **➤ Facing**). Apply
   to the matching `data/murals/{id}-*.yaml` (`facing:` goes under `lng:`;
   `facing: none` = delete the line). Log it in revisionLog + sourceNotes.
2. `# ═══ Route Definition ═══` — a `{ id, name, ids: [...] }` block. Apply the
   `ids` (and name) to that route's entry in `data/routes.json`.
3. `# ═══ Path Changes ═══` — a JSON `"route-id":{"segments":[{"from":N,"to":M,
   "path":[[lat,lng],...]}, ...],"distance":X.XX}` payload. Apply `segments` +
   `distance` to that route's entry in `data/routes.json` (parse-edit-rewrite so
   you don't touch other routes).

Then run `python3 scripts/build-data.py` (regenerates `js/routes.js` +
`js/content.json` from `data/routes.json`) and `publish-content.py` to push the
route live over OTA. The editor's **⚡ Generate Paths** button auto-routes every
leg via Valhalla walking directions (auto-tagged `{from,to,path}`) for the
current stop order — set/reorder stops, click it, tweak outliers, Export Route.

**Verify every leg is tagged** before applying: each consecutive stop pair needs
a `{from,to,path}` segment (loop routes wrap last→first; linear routes like
pinellas-trail don't), else that leg silently falls back to a straight line.

## GOTCHA: routes.js is GENERATED — edit `data/routes.json`

`js/routes.js` (exports `ROUTE_DEFS` + `ROUTE_PATHS`) is **generated by
`build-data.py` from `data/routes.json`** — do NOT hand-edit it (regeneration
overwrites). The runtime expects `segments: [{from, to, path}, ...]` per route;
`app.js` looks segments up by `find(s => s.from === fromId && s.to === toId)`, so
an untagged segment (no from/to) silently breaks per-leg navigation and draws a
straight line. `app.js` imports `ROUTE_DEFS` from `routes.js` (no longer defined
inline); `content.js` overlays newer OTA routes onto `ROUTE_DEFS`/`ROUTE_PATHS`
in place at boot.

**Never run `scripts/build-routes.py` or `scripts/build-routes-osrm.py`** — both
predate this pipeline, emit the wrong format, and overwrite `routes.js`.
`data/routes/*.geojson` are the editor's load state, not the runtime source.

## Build / ship checklist

`npm run cap:sync` (NOT `npx cap sync`) → bump build in `ios/App/App/Info.plist`
and `ios/App/App.xcodeproj/project.pbxproj` → run the archive+export+upload, then
create/attach the App Store version and submit.

**iOS is on the UIScene lifecycle (since build 159) — keep it.** Apps built with the SDK
after iOS 26 must use UIScene or UIKit traps at launch: build 158 (first Xcode 27 build)
crashed on open, `EXC_BREAKPOINT` in UIKitCore. `Info.plist` carries
`UIApplicationSceneManifest` → `SceneDelegate` (defined in `AppDelegate.swift`, which also
forwards URLs/Universal Links to `ApplicationDelegateProxy`). Don't remove either, and
re-add them if the iOS project is ever regenerated (`npx cap add ios` won't). **After any
Xcode update**, run `bash scripts/ios-sim-smoke.sh` before `mq_build.sh` — it builds for the
newest installed iOS simulator, launches, and fails if the app dies. It warns if the newest
simulator runtime is older than the SDK (install it: `xcodebuild -downloadPlatform iOS`),
since an old runtime won't enforce new-SDK launch rules. Then TestFlight on a real phone
before submitting. `mq_build.sh` uses `-sdk iphoneos` (latest) for the same reason.

The whole archive → export → upload is wrapped in `assets/wip/mq_build.sh`
(gitignored — carries ASC account IDs; public repo). It uses **manual signing**
via `assets/wip/ExportOptions-manual.plist` against the Apple Distribution cert
(the account had none — it was created via the ASC API; see MEMORY.md). The
ASC version-create + submit-for-review flow is automated in
`assets/wip/mq_submit.py` (`--submit` to actually submit).

`mq_build.sh` has an **uncommitted-work guard**: it refuses to archive if the git
tree is dirty (so you never ship uncommitted code). Override a deliberate dirty
build with `MQ_ALLOW_DIRTY=1 bash assets/wip/mq_build.sh`. Full details, credentials,
and current build/version status are in MEMORY.md.

**Android is now hands-free too** (set up 2026-08-20). After `gradlew bundleRelease`,
`python3 assets/wip/mq_play_upload.py` uploads the AAB to Play + rolls out via the Play
Developer API — no Play Console clicking (creates edit → resumable-uploads the AAB →
assigns the versionCode to the track with notes → commits + sends for review). Auth is the
service account `play-publisher@mural-quest.iam.gserviceaccount.com` (GCP project
`mural-quest`), key at gitignored **`.mq-play-key.json`**. Needs `google-api-python-client`
+ `google-auth`. Re-using an existing versionCode → 403 "already used" (NOT a permission
error). Keep iOS/Android **version numbers aligned** (they drifted once → realigned at 1.7.3).

**Strip test murals before a production build:** the SHINE test stubs (#900, #999) live in
gitignored **`.mq-held/`** — move them there (out of `data/murals/`) and rebuild so they
don't bundle. See "SHINE 2026 field capture" below and `docs/SHINE-2026-OTA-TEST.md`.

## SHINE 2026 field capture — photo → live over OTA, no build

`tools/mural-capture.html` (Progress Capture PWA on mural-tools.pages.dev) + the
**Capture Worker** `workers/mural-capture/` at **`capture.muralquest.app`** let Rob
photograph an under-construction mural in the field and publish it live. PWA: pick a
mural, live 4K camera with an **onion-skin overlay** of the previous photo for alignment,
capture (≤1600px), Send → `POST /photo` (gated by `POST_KEY`, header `X-Capture-Key`;
key in gitignored `.mq-capture-key`). The Worker (R2 binding to `muralquest-content`)
uploads the frame to `images/murals/2026/<id>-<date>[-N].jpeg` and appends `{u,d}` to the
mural's `ph` in `content.json`, bumps version — live in ~1 min. **Multiple photos/day** get
`-2`,`-3` suffixes. Each photo also carries the geo compass reading at Shoot
(`h`, the way the camera pointed); `publish-content.py` turns it into the mural's
`facing` (view direction = the camera's heading, exported as `fc`, used by `tools/mural-finder.html`) **only when
the YAML has no `facing:` yet** — a facing Rob set in the route editor is never overwritten. The app's build-viewer (`mural.ph`) + "Being painted now" badge render it.

**⚠️ The Worker writes `content.json` DIRECTLY on R2 — it does NOT update the source YAML.**
A Mac `publish-content.py` rebuilds content.json from the YAMLs, so it *would* erase
Worker-added photos. **This is now handled:** `publish-content.py` runs a **reconcile
step first** — it fetches the live manifest and writes each mural's `ph`/`uc` back into
its YAML before the rebuild, so publishing is lossless. It **fails closed**: if the live
manifest can't be fetched, nothing is built or uploaded (`--no-reconcile` overrides, and
will drop any live Worker photos). It also warns loudly when a mural has live photos but
no local YAML (e.g. held in `.mq-held/`) — that mural gets dropped from the manifest.

**Live OTA (v1.7.3):** `content.js` now applies newer content the moment it fetches
(ETag → cheap 304 polling) and re-renders in place; it polls every 15s **only while any
`uc:true` mural exists** (festival mode), idle otherwise. So a new photo pops into an open
app without a restart.

## Bio review tool — field bio edits, approved on the iPad, live over OTA

`tools/bio-review.html` (on mural-tools.pages.dev, iPad-first, works on Mac/phone) lets Rob
review a bio, dictate or type corrections (alone or with the artist), have Claude apply
them, see word-level changes (green = added), edit by hand, then **Approve** or **Approved
by artist**. Backend = `/review/*` routes in the Capture Worker (`src/review.js`), same
`X-Capture-Key`. Recordings → Workers AI Whisper; edits → Claude API (Worker secret
`ANTHROPIC_KEY`). Drafts, the YAML bundle and the approval queue live in the **private**
R2 bucket `muralquest-review` (never the public CDN bucket).

An approval writes the fields straight into content.json (live in ~1 min) **and** queues
them. Like Worker photos, that means a Mac publish would revert them — so
`publish-content.py` first runs `scripts/review_sync.py` `pull_approvals()`, which writes
each queued edit into its YAML with a revisionLog entry (`[review:<id>]` token makes it
idempotent) + sourceNotes, with a **field-level conflict check** (a field changed on the
Mac since the edit was made is not overwritten; the publish aborts until resolved). After
publishing it acks the queue and re-uploads the YAML bundle the tool reads.
`--no-review-pull` skips the pull (reverts live field edits). Standalone:
`python3 scripts/review_sync.py --bundle` / `--queue`. The tool starts in **Dry run**
(Settings) — approvals preview only, nothing written.

## Content OTA (v1.5) — update data WITHOUT an app build

As of v1.5, mural **data** (not the app code or images yet) can be pushed live
over-the-air, bypassing App Store / Play review. Use this for festival daily
updates:

    edit data/murals/*.yaml  →  python3 scripts/publish-content.py  →  live in ~1 min

- `build-data.py` now emits `js/content.json` (the OTA manifest — same short-key
  shape as `data.js`, verified byte-identical) plus `js/content-meta.js` (the
  bundled version marker; tracked). `content.json` is **gitignored** (regenerated +
  uploaded each publish).
- `scripts/publish-content.py` runs `build-data.py`, uploads `content.json` to the
  Cloudflare **R2 bucket `muralquest-content`** (served at `https://cdn.muralquest.app`),
  and verifies the live version. Needs `wrangler` authenticated (`npx wrangler whoami`).
- Client: `js/content.js` fetches the manifest at launch and applies it if newer
  than the bundle (mutating the `murals`/`pois`/`YEARS` arrays in place; all
  existing `app.js` references keep working). Bundled `data.js` is the offline
  fallback — remote is never required. `CONTENT_BASE_URL` in `content.js` = the CDN.
- The service worker (`sw.js`) **bypasses `content.json`** so it can't shadow OTA
  updates with a stale cache. If you touch the SW's fetch routing, preserve that.

### GOTCHA: the editor tools serve a SNAPSHOT, not the repo

`tools/*.html` fetch `../data/murals/*.yaml` **relative to wherever they are served**.
On `mural-tools.pages.dev` that is a point-in-time copy pushed by
`scripts/deploy-tools.sh` — it does **not** re-run on its own. So after editing YAMLs,
the editors keep showing the OLD data and it looks like the publish silently failed.
The app is unaffected (`content.json` goes straight to R2 and is verified each publish).

Refresh it with `python3 scripts/publish-content.py --tools` (publish + redeploy the
snapshot) or `bash scripts/deploy-tools.sh` on its own. `--tools` is **opt-in** on
purpose: it uploads 200+ files and adds ~15s, which you don't want on the festival
photo fast path.

### Image split (v1.5)

The app bundle is ~35 MB (was 414 MB). Full-res photos live on the CDN; a small
bundled **card tier** serves every small display.

- **Cards** — `scripts/generate-cards.py` builds `images/cards/**` (384px WebP,
  ~2.9 MB for 189) from `images/murals/**`, and writes `card-manifest.json` (root;
  the SW precaches from it). Grid, map icons, tour pins/stops, popups, and the
  proximity banner all use cards via `cardSrc()` in app.js.
- **Full-res** — the detail hero uses `fullSrc()` → `cdn.muralquest.app/images/murals/…`.
  `scripts/publish-images.py` uploads cards + full-res to R2 (`--cards-only` for
  just the small tier).
- **Bundle** — `cap:copy` excludes `images/murals` + `images/thumbs` (old 96px,
  superseded) + `audio` (narration streams from the CDN via each mural's `aud`
  URL — the app never reads a bundled copy, so bundling it was ~29 MB of dead
  weight) + `js/content.json`, and uses `--delete --delete-excluded` so `www/`
  is a clean mirror (no stale files). `images/cards` IS bundled.
- **Offline audio** — clips aren't bundled, but the SW **precaches all of them on
  install** into `AUDIO_CACHE` (from `audio-manifest.json`, generated by
  build-data.py — the sorted list of every mural's `aud` URL), so tours play
  offline in dead zones. `/audio/` fetches are cache-first (`cacheFirstAudio`).
  Bump `AUDIO_CACHE`'s version in sw.js only if you need to force clip re-download.
- **onerror fallback** (app.js `mqCardErr`/`mqFullErr`): bundled card → CDN card →
  CDN full → grey; detail full-res → bundled card offline. So OTA-added murals
  (no bundled card) still show via the CDN.

**Adding a mural mid-festival:** add the photo → `generate-cards.py` →
`publish-images.py --cards-only` (upload its card + full-res) → `publish-content.py`
(push the data manifest). The new mural then appears on next app launch, images
served from the CDN.

## Analytics (v1.5) — first-party, self-hosted

Anonymous usage analytics on Cloudflare (no PII, no IP, no cross-app tracking).

- **Worker** `workers/analytics/` → deployed at `analytics.muralquest.app`. `POST /e`
  ingests event batches into **D1** (`mural-quest-analytics`). `GET /stats?key=…`
  returns aggregates (total, sessions, by-event, by-day, top murals); `&from=&to=&tz=` limits
  it to a date range. **Rob's own devices are left out** — their anonymous ids are rows in the
  D1 table `excluded_sids` (add one with a `wrangler d1 execute --remote` INSERT, no deploy);
  `&mine=1` / the stats page's "Include my devices" box puts them back. Deploy with
  `cd workers/analytics && npx wrangler deploy`; schema in `schema.sql`.
- **Client** `js/analytics.js` — `track(event, props)` (also `window.mqTrack`),
  anonymous session id, offline queue, `sendBeacon` flush. Events wired in app.js:
  `app_open`, `screen_view`, `mural_open`, `filter_used`, `search`, `book_card_tap`,
  `book_buy_click`.
- **STATS_KEY** (the `/stats` admin gate) is a Cloudflare Worker **secret** — NOT in
  the repo. Rotate/set with `echo <key> | npx wrangler secret put STATS_KEY` from
  `workers/analytics/`.

**No in-app Instagram feed** (Rob's call — see memory `feedback-no-ig-feed-in-app`).
Instead, a Rob-side tool posts a chosen mural to the Mural Quest IG when he wants.

- **Worker** `workers/ig-feed/` → `ig.muralquest.app`. `POST /post` (gated by
  `POST_KEY` secret) creates + publishes an IG media container from a public image
  URL; holds the `IG_TOKEN` secret (Instagram Login flow, `graph.instagram.com`).
  `?dry=1` creates the container but does NOT publish (safe test).
- **CLI** `scripts/ig_post.py <id>` (or `publish-content.py --post <id>`): builds an
  IG-compliant 1080px image (blurred fill, no bars) → uploads to R2 `images/ig/` →
  drafts a caption from the mural's data (MQ voice) → you edit → confirm → post.
  `--dry-run` tests without publishing; `--caption "…" --yes` scripts it.
- **Secrets:** `IG_TOKEN` (long-lived, expires ~60 days — refresh then re-`secret put`)
  and `POST_KEY` live in the Worker. The local `.mq-ig-post-key` (gitignored) holds
  only the POST key for the CLI. Meta app: "Mural Quest-IG", account
  `mural_quest_st_pete`.
- Future: auto-post caption via Claude API if `ANTHROPIC_API_KEY` is set (currently
  drafts from the mural's existing bio/desc); token auto-refresh cron.
